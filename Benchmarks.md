## Methodology

- **Path measured:** full end-to-end `runEngine` round trip through the real Electron IPC bridge — input approval → worker (native `@napi-rs/canvas` for images, `ffmpeg-static` for media, JSZip/pdf-lib as in the renderer) → output written to the job temp dir → reported to the renderer. Disk I/O, worker startup, and IPC serialization are all included.
- **Repetitions:** 1 warm-up run discarded, then 3 measured iterations per case; the median is reported alongside min/max.
- **Fixtures:** per-pixel noise PNGs (worst case for both decode and encode — no compression anywhere), incompressible random blobs for archives, and pdf-lib documents for PDF merges. Image inputs are labelled by megapixels because byte size of noisy sources is not a meaningful comparison metric.
- **Automation:** `scripts/benchmark-electron.mjs` boots `out/main/main.js` with `--remote-debugging-port=0`, drives `window.fileforge` over the DevTools protocol, and writes `benchmark-results.md`.

## Findings

- **Images:** sub-half-second for all tested sizes. `image.convert → JPEG` scales to 8 MP in ~260 ms. `image.compress` is the slowest image operation (~400 ms at 8 MP) because it re-encodes the source **in its original format** (`image.compress` of a PNG re-encodes to PNG), which is the most expensive path.
- **Archives:** `zip.create` 6 MB ≈ 400 ms; hashing (SHA-256) runs at ~214 MB/s. Both well within "large file operations don't crash" guardrails.
- **PDF:** `pdf.merge` is negligible (~7 ms) for document-scale inputs.
- **Worker isolation:** heavy engines run in a dedicated worker pool (max `CPU-1`), so these times do not block the UI thread.

## Reproducibility

```bash
npm run build:electron   # rebuild first so the benchmark runs the current code
npm run benchmark:electron   # defaults to 3 iterations + 1 warm-up
$env:BENCH_ITERATIONS = "5"; npm run benchmark:electron   # more samples (optional)
```

Numbers are environment-dependent; compare relative shapes on a single machine rather than exact values across machines.

## Scope note: web (WASM) comparison

The web PWA and the desktop app intentionally use different engines — the web stack routes images/media through `@ffmpeg/ffmpeg` WASM and browser canvas, while the desktop build uses native workers. A direct web-vs-desktop number comparison would be misleading, so it is **not** included in the automated benchmark. Where both stacks share the same library (JSZip, pdf-lib), behavior is identical by construction; a browser-side performance pass remains future work.
